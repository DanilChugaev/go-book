# Вклад в учебник Go

Спасибо за интерес к проекту. Подходят исправления фактов, формулировок, ссылок и опечаток, улучшения примеров и заданий, а также предложения по программе. Цель вклада — сделать материал понятнее, точнее и воспроизводимее для начинающего разработчика.

Перед участием прочитайте [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) и [SECURITY.md](SECURITY.md).

## До начала работы

1. Проверьте [открытые issues](https://github.com/DanilChugaev/go-book/issues), чтобы не дублировать работу.
2. Для большой темы сначала создайте issue и кратко опишите проблему, аудиторию, план и пример результата.
3. Не объединяйте несвязанные изменения в одном pull request.

## Локальная среда

Нужны Node.js LTS и npm. Репозиторий использует `package-lock.json`.

```bash
git clone https://github.com/DanilChugaev/go-book.git
cd go-book
npm ci
npm run docs:dev
```

Dev-сервер доступен на [http://localhost:6060/go-book/](http://localhost:6060/go-book/).

Перед pull request обязательно выполните:

```bash
npm run docs:build
git diff --check
```

Для изменений во фронтенде (или целиком по проекту) удобнее `npm run verify` — он запускает тесты, ESLint, проверку Prettier, сборку книги и `git diff --check` одной цепочкой.

Если меняются Go-примеры, запускайте и указывайте в PR релевантные команды:

```bash
gofmt -w <изменённые-файлы>
go vet ./...
go test ./...
go test -race ./...
```

Не добавляйте в commit временные Go-модули, базы данных, Docker volumes, `node_modules` и другие локальные артефакты.

## Ветка и pull request

Создайте ветку от актуального `master`:

```bash
git switch master
git pull --ff-only origin master
git switch -c docs/short-description
```

В pull request:

- используйте ясный заголовок, например `docs: clarify Context cancellation`;
- свяжите PR с issue через `Fixes #123`, если он его решает;
- перечислите изменённые страницы и мотивацию;
- сообщите команды проверки и их результат;
- приложите скриншот для заметного изменения интерфейса или layout;
- оставьте scope небольшим и готовым к review.

Не отправляйте secrets, `.env`, access tokens, локальные пути, сгенерированный `docs/.vuepress/dist/` или случайные изменения lock-файла.

## Стиль материалов

- Пишите по-русски, ясно и дружелюбно, обращаясь к читателю на «вы».
- Объясняйте термин при первом появлении; английские API оставляйте в code format.
- Для новых глав соблюдайте порядок: цель → теория → частые ошибки → самопроверка → задания → рекомендации по коду.
- Задания оформляйте как: задача → критерии проверки → подсказка → скрытое решение.
- Не обещайте поведение, которое пример не демонстрирует и не проверяет.
- Отделяйте учебное упрощение от production-рекомендации.
- При описании API указывайте метод, путь, статусы, JSON-контракт и ошибки.

## Требования к примерам кода

- Пример должен компилироваться в заявленном контексте или явно указывать опущенные зависимости.
- Используйте `gofmt` и идиоматичные имена Go.
- Не игнорируйте ошибки без пояснения, почему это допустимо в учебном фрагменте.
- Передавайте `context.Context` в отменяемые внешние и SQL-операции.
- Не храните секреты, токены, пароли и персональные данные в примерах.
- Для конкурентного кода избегайте `time.Sleep` в тестах, если доступна детерминированная синхронизация.

## Стиль фронтенд-кода (Vue)

Интерфейс учебника живёт в `docs/.vuepress/**` и `docs/*.ts`: Vue 3 SFC с `<script setup lang="ts">`, SCSS с BEM-именованием. Формат и lint держат Prettier и ESLint (`.prettierrc`, `eslint.config.mjs`).

- Перед коммитом запускайте `npm run format`; pre-commit в любом случае прогоняет `npm run verify`.
- В template разделяйте логические блоки пустой строкой: ветки `v-if`/`v-else-if`/`v-else`, несколько `<template>` в одном родительском элементе. Prettier сохраняет пустые строки между элементами, но сам их не добавляет — вставляйте вручную.
- Если атрибуты тега не влезают в одну строку, закрывающая скобка `>` стоит в конце последней строки атрибутов (настройка `bracketSameLine`), а содержимое идёт с новой строки. Не прилипайте содержимое к скобке (`><code>`) и не оставляйте «висящую» `>` на отдельной строке.

## Зависимости и review

Не обновляйте зависимости «заодно». Отдельный dependency PR должен объяснять причину, содержать актуальный `package-lock.json` и проходить сборку. Dependabot создаёт PR для npm- и GitHub Actions-зависимостей; перед merge всё равно проверяйте release notes, совместимость и CI.

Maintainер может попросить сократить scope, разделить PR, уточнить источник утверждения, добавить тест или изменить формулировку. Merge выполняет maintainер после прохождения CI и review.
