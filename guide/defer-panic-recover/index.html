defer, panic и recover

Цель урока

Научиться гарантированно освобождать ресурсы через defer, понимать разницу между ожидаемой ошибкой и panic, а также применять recover только на чёткой границе аварийного сценария.

Главное практическое применение defer в Task Manager API — закрытие файлов. panic и recover нужны гораздо реже: они не заменяют обычную обработку error.

defer: выполнить перед выходом из функции

defer откладывает вызов до момента, когда текущая функция завершится — обычным return или из-за panic:

package main

import "fmt"

func main() {
	defer fmt.Println("Выполнится последним")

	fmt.Println("Выполнится первым")
}

Вывод:

Выполнится первым
Выполнится последним

defer полезен для действий, которые должны произойти независимо от того, по какому пути функция завершится:

  • закрыть файл;
  • разблокировать mutex;
  • вызвать cancel у context;
  • вернуть соединение в пул;
  • записать завершающий лог.

Закрытие файла через defer

После успешного открытия файла сразу запланируйте закрытие:

func readExport(path string) error {
	file, err := os.Open(path)
	if err != nil {
		return fmt.Errorf("не удалось открыть экспорт: %w", err)
	}
	defer file.Close()

	content, err := io.ReadAll(file)
	if err != nil {
		return fmt.Errorf("не удалось прочитать экспорт: %w", err)
	}

	fmt.Print(string(content))
	return nil
}

Если io.ReadAll вернёт ошибку, return завершит функцию, а затем Go вызовет file.Close().

Важно ставить defer file.Close() только после проверки ошибки os.Open: до успешного открытия file может быть nil.

Значения аргументов вычисляются сразу

Аргументы отложенного вызова вычисляются в момент defer, а не в момент выполнения:

func main() {
	name := "Купить молоко"
	defer fmt.Println(name)

	name = "Купить продукты"
}

Вывод будет:

Купить молоко

Если нужен актуальный результат на момент выхода, используйте отложенную анонимную функцию:

defer func() {
	fmt.Println(name)
}()

Теперь будет выведено Купить продукты, потому что переменная читается внутри функции во время её запуска.

Несколько defer: порядок LIFO

Несколько отложенных вызовов выполняются в обратном порядке — последний добавленный выполняется первым:

func main() {
	defer fmt.Println("Первый defer")
	defer fmt.Println("Второй defer")
	defer fmt.Println("Третий defer")
}

Вывод:

Третий defer
Второй defer
Первый defer

Это правило называют LIFO: last in, first out. Оно естественно освобождает ресурсы в обратном порядке их захвата.

Ошибка Close

Для чтения ошибка при закрытии файла встречается редко, поэтому в простом коде часто достаточно defer file.Close(). При записи Close может вернуть важную ошибку: например, операционная система может обнаружить проблему при финальной записи буферов.

Если ошибку закрытия нужно вернуть, используйте именованный результат и отложенную функцию:

func writeExport(path, content string) (err error) {
	file, err := os.Create(path)
	if err != nil {
		return fmt.Errorf("не удалось создать экспорт: %w", err)
	}

	defer func() {
		closeErr := file.Close()
		if err == nil && closeErr != nil {
			err = fmt.Errorf("не удалось закрыть экспорт: %w", closeErr)
		}
	}()

	if _, err := file.WriteString(content); err != nil {
		return fmt.Errorf("не удалось записать экспорт: %w", err)
	}

	return nil
}

Логика важна:

  1. если запись уже завершилась ошибкой, она остаётся основной причиной;
  2. если запись успешна, но Close не удался, возвращается ошибка закрытия;
  3. файл закрывается при любом return после defer.

Для небольшого экспорта через os.WriteFile закрытие управляется стандартной библиотекой, поэтому вручную применять этот паттерн не нужно.

panic

panic означает аварийную ситуацию: текущая функция прекращает нормальное выполнение, запускаются отложенные вызовы, затем panic поднимается вверх по стеку. Если её никто не восстановил, программа завершается со stack trace.

func main() {
	panic("неожиданное состояние")
}

Не используйте panic для ожидаемых ситуаций:

  • пользователь передал пустое название;
  • файл не существует;
  • сеть недоступна;
  • задача не найдена.

Во всех этих случаях вызывающий код может принять решение, поэтому возвращайте error.

Panic допустим только для действительно невозможного состояния программы или нарушения внутреннего инварианта, которое нельзя разумно обработать на текущем уровне. В прикладном коде Task Manager API такие случаи должны быть редкими.

recover

recover перехватывает активную panic, но работает только внутри функции, вызванной через defer в той же goroutine:

func safeRun() {
	defer func() {
		if recovered := recover(); recovered != nil {
			fmt.Println("Перехвачена panic:", recovered)
		}
	}()

	panic("ошибка демонстрации")
}

После recover функция, в которой произошла panic, не продолжает выполнение с места panic. Управление возвращается из неё после выполнения отложенных функций.

Не превращайте recover в обычный error handling

recover не должен окружать каждую функцию и скрывать ошибки. Он полезен на ограниченной границе: например, в верхнем уровне сервера, в изолированной фоновой задаче или в библиотеке, которая защищает внешний API. Причину panic нужно залогировать и расследовать.

Panic и goroutine

Panic в одной goroutine не может быть перехвачена recover из другой goroutine:

func main() {
	defer func() {
		recover() // Не перехватит panic из go func().
	}()

	go func() {
		panic("авария в goroutine")
	}()
}

Если отдельная goroutine действительно должна быть защищена от panic, recover нужно разместить внутри неё. Но сначала исправьте причину panic: recover — последний защитный слой, а не замена корректному коду.

Task Manager API: безопасная запись экспорта

Для записи небольшого tasks.txt удобнее os.WriteFile. Но при работе с открытым *os.File функция Task Manager API должна гарантированно закрывать его:

func writeTextExport(path, content string) (err error) {
	file, err := os.Create(path)
	if err != nil {
		return fmt.Errorf("не удалось создать текстовый экспорт: %w", err)
	}

	defer func() {
		closeErr := file.Close()
		if err == nil && closeErr != nil {
			err = fmt.Errorf("не удалось закрыть текстовый экспорт: %w", closeErr)
		}
	}()

	if _, err := file.WriteString(content); err != nil {
		return fmt.Errorf("не удалось записать текстовый экспорт: %w", err)
	}

	return nil
}

Эта функция не использует panic: ошибки файловой системы ожидаемы и должны вернуться вызывающему коду как error.

Частые ошибки

defer до проверки ошибки

file, err := os.Open(path)
defer file.Close() // file может быть nil

if err != nil {
	return err
}

Правильно сначала проверить err, затем отложить закрытие.

Забытый Unlock

store.mu.Lock()
if invalid {
	return // мьютекс остался заблокирован
}
store.mu.Unlock()

Сразу после успешного Lock используйте defer store.mu.Unlock().

recover вне defer

recovered := recover() // ничего не перехватит

recover работает только в отложенной функции во время раскручивания panic.

Panic для ошибки валидации

if title == "" {
	panic("пустое название")
}

Верните ErrEmptyTitle: пользовательский ввод — ожидаемая ошибка, а не авария процесса.
