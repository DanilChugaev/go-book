panic и recover в библиотечном коде

Сначала правило по умолчанию

Библиотечный код должен возвращать error для ожидаемых неудач. Неверный ввод, недоступная БД, отменённый context, отсутствие файла и ответ внешнего HTTP-сервиса — это не повод для panic.

// Неверно: пользовательский ввод — ожидаемая ситуация.
func NewTask(title string, priority int) Task {
	if title == "" {
		panic("title is required")
	}
	return Task{Title: title, Priority: priority}
}

// Верно: вызывающий код выбирает, как сообщить о проблеме.
func NewTask(title string, priority int) (Task, error) {
	if err := validateCreateInput(title, priority); err != nil {
		return Task{}, err
	}
	return Task{Title: title, Priority: priority}, nil
}

panic прерывает обычный поток управления. Пока стек раскручивается, вызываются defer; если panic не перехватить, завершается весь процесс. Поэтому это инструмент для нарушенного внутреннего инварианта или строго ограниченной защитной границы, а не альтернативная форма error.

Что recover действительно может перехватить

recover срабатывает только если он вызван непосредственно из отложенной функции в той же goroutine, пока эта goroutine раскручивает panic:

func callSafely(fn func()) (panicked bool) {
	defer func() {
		if recovered := recover(); recovered != nil {
			panicked = true
		}
	}()

	fn()
	return false
}

После восстановления функция, в которой началась panic, не продолжает работу с точки panic. В примере выше callSafely завершится с true.

recover за пределами defer вернёт nil. Вызов из вспомогательной функции также не является надёжной заменой прямому вызову в отложенной функции. Делайте recovery-блок коротким и видимым рядом с границей, которую он защищает.

recover не пересекает goroutine

Такой код не защитит процесс:

func wrong() {
	defer func() {
		recover()
	}()

	go func() {
		panic("panic в фоновой задаче")
	}()
}

У каждой goroutine свой стек. Если вы запускаете изолированную пользовательскую callback-функцию или worker и по контракту не хотите дать ей завершить весь процесс, recovery должен находиться внутри этой goroutine:

func runWorker(logger *slog.Logger, work func()) {
	go func() {
		defer func() {
			if recovered := recover(); recovered != nil {
				logger.Error("panic в изолированном worker", "recovered", recovered)
			}
		}()

		work()
	}()
}

Это последний барьер, а не доказательство, что worker безопасен. Нужно решить, что делать с частично записанными данными, состоянием очереди и возможной повторной задачей. Для критичных операций обычно важнее транзакция, идемпотентность и корректная обработка error.

Когда library boundary действительно оправдана

Иногда библиотека вызывает код, который ей не принадлежит: плагины, callbacks, пользовательские шаблоны, тестовые хуки. Если паника такого callback не должна разрушить основной процесс, библиотека может превратить её в отдельную, документированную ошибку.

type PanicError struct {
	Value any
}

func (err *PanicError) Error() string {
	return "callback завершился panic"
}

func RunCallback(callback func() error) (err error) {
	defer func() {
		if recovered := recover(); recovered != nil {
			err = &PanicError{Value: recovered}
		}
	}()

	return callback()
}

Пользователь API может различить нормальную ошибку callback и нарушенный контракт callback:

err := RunCallback(func() error {
	panic("не должен падать")
})

var panicErr *PanicError
if errors.As(err, &panicErr) {
	// Зафиксировать инцидент, остановить конкретную задачу,
	// не отправлять Value клиенту.
}

Этот дизайн оправдан только при явном обещании RunCallback: callback изолирован, а его panic становится ошибкой. Не оборачивайте так все функции пакета «на всякий случай»: это превращает дефект программы в обычную ветку, лишает stack trace и затрудняет расследование.

Не теряйте диагностику

В HTTP boundary или worker обычно нужно залогировать panic вместе со stack trace, но не вернуть его клиенту:

func recoverWorker(logger *slog.Logger) {
	if recovered := recover(); recovered != nil {
		logger.Error(
			"panic в worker",
			"recovered", recovered,
			"stack", string(debug.Stack()),
		)
	}
}

func runWorker(logger *slog.Logger, work func()) {
	go func() {
		defer recoverWorker(logger)
		work()
	}()
}

Stack trace может содержать внутренние пути, аргументы или иные чувствительные данные. Он предназначен для защищённого журнала, а не для JSON-ответа, метрики с неограниченной кардинальностью или сообщения пользователю. Проверьте политику хранения логов до добавления таких полей.

В библиотеке чаще лучше вернуть PanicError без stack trace. Верхняя граница приложения решает, нужно ли писать стек, в какой лог и как его защитить.

panic как намеренный контракт

Некоторые API стандартной библиотеки паникуют при нарушении программистского контракта: например, индекс вне границ слайса. Свой API может использовать такой подход только если одновременно выполняются условия:

  • ошибка означает баг вызывающего программиста, а не входные данные пользователя или внешнюю среду;
  • проверка возвращаемого error сделала бы API существенно хуже, а не просто короче;
  • поведение ясно отражено в имени и документации;
  • panic не оставляет систему в тихо повреждённом состоянии.

Честный вариант — отдельный helper с префиксом Must:

func MustParseDuration(value string) time.Duration {
	duration, err := time.ParseDuration(value)
	if err != nil {
		panic(fmt.Sprintf("некорректная duration %q: %v", value, err))
	}
	return duration
}

Такой helper уместен для константной конфигурации в main или тестах, когда ошибка означает дефект исходного кода. Он не подходит для переменной окружения или тела HTTP-запроса: там вместо него нужна функция с error и понятной диагностикой запуска либо ответа клиенту.

panic, os.Exit и cleanup

При panic выполняются отложенные вызовы текущего стека. При os.Exit — нет. Поэтому package-код не должен вызывать os.Exit: он не даёт вызывающему коду закрыть БД, дописать лог, снять lock или проверить ошибку в тесте.

// В библиотеке плохо:
if err != nil {
	os.Exit(1)
}

// Библиотека возвращает ошибку; main принимает решение о процессе.
if err != nil {
	return fmt.Errorf("запустить приложение: %w", err)
}

main — естественная граница, где допустимы окончательный лог и ненулевой код завершения. Даже там предпочтительнее дать run() вернуть ошибку, а не рассыпать os.Exit по зависимостям.

Чек-лист перед recover

Перед добавлением recovery-блока спросите себя:

  1. Можно ли устранить причину и вернуть обычный error?
  2. Какая конкретная граница изолируется: HTTP-запрос, callback, отдельный worker?
  3. Что произойдёт с частично изменёнными данными?
  4. Где будут записаны причина и stack trace?
  5. Как гарантировать, что клиент не увидит внутреннюю информацию?
  6. Как тест докажет, что recovery не скрывает нормальные ошибки и не завершает процесс?
