# Рекомендации по коду: ошибки и ресурсы

## Ошибки как контракт пакета

- Добавляйте контекст операции через `fmt.Errorf("...: %w", err)`, но осознанно: `%w` делает внутреннюю причину доступной вызывающему коду.
- Используйте `errors.Is` для известных причин-маркеров (`ErrTaskNotFound`, `context.Canceled`, `sql.ErrNoRows` на подходящей границе).
- Используйте `errors.As`, когда вызывающему коду нужны данные собственного типа ошибки, а не только факт причины.
- Документируйте экспортируемые ошибки, их поля и допустимые значения так же, как публичные функции.
- Не сравнивайте `err.Error()`; текст меняется и предназначен для диагностики, а не для ветвления.
- Не возвращайте typed `nil` как `error`: при успехе возвращайте именно `nil`.
- Объединяйте причины через `errors.Join` только когда несколько независимых ошибок действительно нужны для диагностики или cleanup.
- Не раскрывайте клиентам технические ошибки драйверов, сетевых библиотек и stack trace.

## Владение и `defer`

- Сразу после успешного получения ресурса решайте, кто его освобождает; если владение не передано явно, закрывайте ресурс в той же функции.
- Регистрируйте `defer` сразу после успешных `Open`, `Lock`, `BeginTx`, `WithTimeout` и `client.Do`.
- Помните LIFO: зависимые ресурсы освобождаются в обратном порядке их захвата. Буфер нужно `Flush` до закрытия файла.
- Для операций записи выбирайте явную политику ошибки `Close`; если важны обе причины, не потеряйте их через `errors.Join`.
- Не откладывайте `Close`, `cancel` или `Unlock` в длинном цикле до конца внешней функции. Вынесите одну итерацию в helper или завершайте ресурс явно.
- Не удерживайте mutex во время сети, SQL, файлового ввода-вывода и других медленных операций.
- Для транзакции ставьте `defer tx.Rollback()` сразу после успешного `BeginTx`, а `Commit` делайте только после всех успешных операций.

## `panic`, `recover` и границы процесса

- Возвращайте `error` для ожидаемых проблем пользователя, сети, файла, БД и конфигурации окружения.
- Применяйте `panic` только для нарушения программистского инварианта с ясно документированным контрактом; helper, который может паниковать, называйте с префиксом `Must`.
- `recover` размещайте только на конкретной изолирующей границе: в HTTP middleware, callback boundary или внутри отдельной goroutine worker.
- Помните: `recover` не перехватывает panic другой goroutine.
- После recovery логируйте причину и stack trace только в защищённый внутренний журнал; не отправляйте их клиенту.
- Не вызывайте `os.Exit` из library-кода: он не запускает `defer` и лишает вызывающий код возможности завершить cleanup. Возвращайте ошибку в `main`.

## HTTP API и логи

- Переводите технические причины в доменные ошибки ниже HTTP-слоя; handler не должен знать детали PostgreSQL или конкретного HTTP-клиента.
- Централизуйте соответствие «доменная ошибка → HTTP status → публичный code/message», чтобы разные handlers не расходились в контракте.
- Пусть клиент ориентируется на стабильный `code`, а не на локализуемое `message`.
- После `c.JSON` или `c.AbortWithStatusJSON` делайте `return`, если handler не должен продолжать работу.
- Ожидаемые `4xx` обычно видны в access log и не требуют error-log на каждом слое. Непредвиденный `5xx` логируйте один раз на границе с request ID и внутренней причиной.
- Проверяйте тестами статус, JSON-код, безопасное сообщение и отсутствие внутренних деталей; не делайте текст логов частью случайного публичного контракта.

## Итоговый чек-лист

Перед merge спросите:

- [ ] Может ли вызывающий код обработать ошибку без разбора её текста?
- [ ] Не раскрывает ли `%w` техническую зависимость за пределами нужного пакета?
- [ ] Закрывается ли каждый полученный ресурс на всех путях, включая ранний `return`?
- [ ] Не накапливает ли `defer` ресурсы внутри цикла?
- [ ] Сохраняется ли значимая ошибка `Close`, `Flush`, `Commit` или cleanup?
- [ ] Есть ли конкретная причина для `panic` или `recover`, а не желание «чтобы не падало»?
- [ ] Безопасен ли JSON-ответ при `500` и можно ли найти внутреннюю причину по одному логу?
- [ ] Зафиксированы ли тестом все документированные ошибки и HTTP-коды?
