# Рекомендации по коду: конкурентные паттерны

## Жизненный цикл goroutine

- Создавайте goroutine только с явной причиной, владельцем и проверяемым путём завершения.
- Для каждой goroutine определите: кто запускает, кто ждёт, какой сигнал останавливает и что происходит с её ошибкой.
- Передавайте `context.Context` первым параметром в отменяемые операции; не создавайте `context.Background()` внутри worker вместо контекста операции.
- В каждом потенциально блокирующем send/receive pipeline добавляйте путь `<-ctx.Done()`, если downstream может закончить раньше.
- Не используйте `time.Sleep` для синхронизации. Каналы событий, `WaitGroup`, `errgroup.Wait` и `done` создают детерминированный контракт.

## Каналы, pool и backpressure

- Закрывает канал только владелец всех отправок — после последней отправки. Consumer не закрывает входной канал.
- При нескольких sender используйте координатор: `WaitGroup.Wait()` → `close(out)` ровно один раз.
- Worker pool применяйте для ограниченного числа живых worker и долгого/неограниченного потока jobs.
- Semaphore на buffered channel подходит для ограничения активных операций, но не ограничивает число goroutine, ожидающих token.
- Буфер выбирайте как конечную очередь с объяснённым размером. Он сглаживает краткие всплески, но не исправляет постоянно медленный consumer.
- Не закрывайте channel-семафор: его жизненный цикл выражают отмена, прекращение создания работ и ожидание группы.
- Не полагайтесь на порядок результатов после fan-out; восстанавливайте его отдельным бизнес-этапом при необходимости.

## Ошибки, отмена и shutdown

- Выберите семантику до реализации: fail-fast с `errgroup.WithContext` или best-effort с полным отчётом ошибок.
- `errgroup` отменяет context при первой ошибке, но не убивает goroutine: каждый downstream вызов обязан замечать отмену.
- Вызывайте `SetLimit` до запуска функций и не меняйте лимит, пока группа активна.
- Не запускайте новые `errgroup.Go` после начала `Wait`.
- При graceful shutdown сначала остановите приём новой работы, затем обработайте/отмените уже принятую по явной политике, дождитесь worker до deadline и только потом закройте зависимости.
- Не обещайте drain и не отменяйте рабочий context немедленно: это противоречивые семантики. Для незавершённых jobs в production определите durable handoff или retry policy.
- Не закрывайте БД и HTTP-клиент, пока активные handler/worker могут ими пользоваться.

## Утечки и диагностика

- Считайте зависший send, receive, `Wait`, lock или I/O без deadline потенциальной утечкой, пока не доказан путь завершения.
- Закрывайте `response.Body`, вызывайте `cancel`, `Rollback`, `Unlock` и возврат semaphore token на всех путях через `defer` после успешного захвата ресурса.
- Запускайте `go test -race ./...` и повторяйте чувствительные тесты с `-count`; race detector не находит все deadlock и leaks.
- Применяйте `go test -timeout` для диагностики зависаний и читайте stack trace как граф producer, consumer и сигналов остановки.
- Исследуйте устойчивый рост `runtime.NumGoroutine()` через goroutine profile; не маскируйте проблему бесконечным буфером.
- Не открывайте `net/http/pprof` публично: профили содержат внутреннюю информацию приложения.

## Итоговый чек-лист

- [ ] У каждой goroutine есть владелец, error path и условие завершения.
- [ ] Для каждого канала известны sender, consumer и единственный закрывающий код.
- [ ] Все блокирующие точки участвуют в отмене там, где операция может стать неактуальной.
- [ ] Число worker, активных операций и размер очереди имеют обоснованные лимиты.
- [ ] Семантика ошибок — fail-fast либо best-effort — отражена в API и тестах.
- [ ] Shutdown не допускает send в закрытый канал и не закрывает зависимости раньше worker.
- [ ] Конкурентные тесты проходят с `-race`, повтором и контролируемыми событиями без `Sleep`.
