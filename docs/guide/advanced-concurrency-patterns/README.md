# Продвинутый Go C: конкурентные паттерны

## Цель главы

Научиться строить ограниченную и отменяемую конкурентную работу: выбирать worker pool, fan-out/fan-in или pipeline, распространять `context` между goroutine, корректно останавливать группу работников и находить утечки goroutine.

Основные главы уже показали `go`, каналы, `WaitGroup`, `select`, `Mutex` и `context`. Здесь важна не новая синтаксическая конструкция, а проектирование полного жизненного цикла:

```text
создать работу → ограничить параллелизм → передать результат
      ↓                  ↓                       ↓
принять отмену ← закрыть каналы владельцем ← дождаться завершения
```

Конкурентный код полезен только тогда, когда независимые операции действительно могут перекрываться: запросы к нескольким внешним сервисам, обработка списка файлов, отправка уведомлений. Он увеличивает число состояний, поэтому сначала нужен понятный последовательный вариант, измерение или явная причина для параллелизма.

## Прежде чем запускать goroutine

Для каждой новой goroutine должен быть ответ на пять вопросов:

1. **Кто её запускает?** Где находится владелец жизненного цикла?
2. **Когда она заканчивает работу?** Закрытие канала, отмена context, конечное число задач, сигнал shutdown?
3. **Как она сообщает об ошибке или результате?** Канал, возвращаемая ошибка `errgroup`, callback, запись в защищённое хранилище?
4. **Что случится, если получатель больше не ждёт?** Отправитель не должен навечно заблокироваться.
5. **Кто и когда ждёт её завершения?** `WaitGroup`, `errgroup.Wait`, отдельный done-канал?

Если хотя бы один пункт неясен, добавление `go` почти наверняка создаст зависание, утечку или непредсказуемое завершение процесса.

## Зачем ограничивать параллелизм

Наивный подход запускает goroutine для каждой задачи:

```go
for _, id := range taskIDs {
	go refreshPriority(ctx, id)
}
```

Для пяти задач это может быть приемлемо. Для десяти тысяч он создаст тысячи одновременных запросов, соединений, таймеров и объектов в памяти. Внешний сервис может получить всплеск нагрузки, локальный HTTP transport — исчерпать соединения, а база — connection pool.

Больше goroutine не означает быстрее. Реальная верхняя граница определяется самым дефицитным ресурсом: лимитом API, числом соединений БД, CPU, памятью, файловыми дескрипторами или допустимой задержкой.

## Worker pool

Worker pool создаёт фиксированное число worker-goroutine. Они читают задания из общего канала, пока producer не закроет его или общий context не будет отменён.

Для примера Task Manager обновляет подсказки приоритета задач через внешний клиент:

```go
type PriorityRefresher interface {
	Refresh(ctx context.Context, taskID TaskID) error
}

func RefreshPriorities(
	ctx context.Context,
	refresher PriorityRefresher,
	taskIDs []TaskID,
	workerCount int,
) error {
	if workerCount < 1 {
		return errors.New("число worker должно быть больше нуля")
	}

	jobs := make(chan TaskID)
	var workers sync.WaitGroup
	var errorsMu sync.Mutex
	var refreshErrors []error

	worker := func() {
		defer workers.Done()
		for {
			select {
			case <-ctx.Done():
				return
			case taskID, open := <-jobs:
				if !open {
					return
				}
				if err := refresher.Refresh(ctx, taskID); err != nil {
					errorsMu.Lock()
					refreshErrors = append(refreshErrors,
						fmt.Errorf("обновить приоритет задачи %d: %w", taskID, err),
					)
					errorsMu.Unlock()
				}
			}
		}
	}

	workers.Add(workerCount)
	for range workerCount {
		go worker()
	}

	for _, taskID := range taskIDs {
		select {
		case <-ctx.Done():
			close(jobs)
			workers.Wait()
			return errors.Join(append(refreshErrors, ctx.Err())...)
		case jobs <- taskID:
		}
	}

	close(jobs)
	workers.Wait()
	return errors.Join(refreshErrors...)
}
```

Этот вариант имеет политику **best-effort**: ошибка одной задачи сохраняется, но другие задачи продолжают выполняться; после завершения pool вызывающий получает `errors.Join`. Доступ к `refreshErrors` защищён mutex, а чтение происходит только после `workers.Wait`. Для политики fail-fast лучше применить `errgroup` на следующей странице.

### Инварианты worker pool

- `workerCount` ограничивает число одновременно выполняемых `Refresh`;
- только producer закрывает `jobs`, потому что он единственный знает, что заданий больше не будет;
- worker не закрывает `jobs`: у него есть конкурирующие отправители/получатели и нет права решать за producer;
- `Wait` вызывается после закрытия/отмены входного потока, чтобы worker успели выйти;
- каждый блокирующий `send` и `receive` участвует в `select` с `ctx.Done()` там, где отмена должна его разблокировать.

## Буфер jobs и backpressure

Небуферизированный `jobs` даёт немедленный backpressure: producer может передать следующее задание, только когда какой-то worker готов принять текущее.

```text
producer ── job ──► свободный worker
    ▲                    │
    └──── ждёт, пока ────┘
```

Буфер разрешает producer опередить worker лишь на ограниченное число заданий:

```go
jobs := make(chan TaskID, workerCount*2)
```

Это полезно, если получение следующего задания очень дёшево, а небольшая очередь сглаживает короткие колебания скорости. Но буфер не является «ускорителем» сам по себе и не решает бесконечный входной поток. Когда буфер заполнен, отправка снова блокируется — это и есть backpressure.

Выбирайте размер из ограничений системы, а не из случайного большого числа:

| Сценарий | Типичное решение |
| --- | --- |
| Нужна строгая естественная обратная связь | небуферизированный канал или маленький буфер |
| Нужно кратко сгладить разную скорость этапов | ограниченный буфер с объяснённым размером |
| Вход быстрее обработки постоянно | ограничить/отклонить вход, сохранять в устойчивую очередь или изменить продуктовую политику |
| Нельзя потерять события | не заменять переполнение бесконечной памятью; использовать durable broker/БД и подтверждения |

`len(jobs)` и `cap(jobs)` подходят для наблюдаемости или отладки, но не для решения «можно ли отправить»: между проверкой и send состояние меняется другой goroutine. Сам `select`/send — единственная надёжная синхронизация.

## Ограничение параллелизма семафором на buffered channel

Если задачи уже запускаются в разных местах и не нужен общий job queue, ограничить одновременно активные операции можно каналом-семафором:

```go
func RefreshAll(ctx context.Context, client PriorityRefresher, taskIDs []TaskID, limit int) error {
	if limit < 1 {
		return errors.New("limit должен быть больше нуля")
	}

	semaphore := make(chan struct{}, limit)
	var group sync.WaitGroup
	errs := make(chan error, len(taskIDs))

	for _, taskID := range taskIDs {
		select {
		case semaphore <- struct{}{}:
		case <-ctx.Done():
			group.Wait()
			return ctx.Err()
		}

		group.Add(1)
		go func(id TaskID) {
			defer group.Done()
			defer func() { <-semaphore }()

			if err := client.Refresh(ctx, id); err != nil {
				select {
				case errs <- fmt.Errorf("обновить приоритет задачи %d: %w", id, err):
				case <-ctx.Done():
				}
			}
		}(taskID)
	}

	group.Wait()
	close(errs)

	var allErrors []error
	for err := range errs {
		allErrors = append(allErrors, err)
	}
	return errors.Join(allErrors...)
}
```

Семафор содержит token для каждой активной операции. Отправка token перед запуском блокируется, когда достигнут `limit`; defer возвращает token при любом выходе worker. Канал ошибок имеет буфер длиной входа, поэтому worker не зависнет, если сбор ошибок начнётся только после `Wait`.

Однако эта модель всё ещё создаёт по goroutine на каждую задачу — просто часть из них ждёт token до запуска. Для большого или неограниченного потока лучше worker pool: он ограничивает и число активных запросов, и число живых goroutine. Для fail-fast политики пример с семафором также неудобнее: следующая страница покажет `errgroup.SetLimit`.

::: warning Не закрывайте семафор
Семафор — это не поток данных. Его обычно не закрывают: завершение работы выражают context, прекращением создания новых задач и ожиданием `WaitGroup`/`errgroup`. Закрытие может привести к успешному receive нулевого значения и запутать протокол.
:::

## Когда pool не нужен

- Операции зависят друг от друга: сначала нужно получить задачу, затем только для неё запросить приоритет. Это больше похоже на pipeline.
- Есть несколько заранее известных независимых операций: часто достаточно нескольких `errgroup.Go`.
- Операция CPU-bound, а лимит определяется числом ядер и измерениями, а не произвольным числом worker.
- Нужна очередь между процессами, повторная доставка после рестарта или приоритеты: канал в памяти не заменяет durable queue.
