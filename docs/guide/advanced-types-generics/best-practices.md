# Рекомендации по коду: типы и generics

## Defined types и alias

- Создавайте defined type через `type Name BaseType`, когда нужно выразить доменный смысл, предотвратить путаницу значений или добавить методы.
- Используйте type alias через `type Name = ExistingType` главным образом для совместимости, миграции или переэкспорта; alias не добавляет типобезопасность.
- Валидируйте внешние данные до преобразования в domain type: `TaskID(value)` не делает ID существующим или положительным.
- Не плодите типы для каждого поля. Новый тип должен улучшать читаемость, защищать реальную границу или нести собственное поведение.
- Не пытайтесь добавлять методы к типам из другого пакета; используйте обёртку, helper или композицию.

## Generic-функции и constraints

- Обобщайте алгоритм, а не бизнес-сущность. `Contains`, `Clone` и `Set` могут быть универсальны; создание задачи и HTTP-контракт — обычно нет.
- Начинайте с самого слабого constraint: `any`, если операции над `T` не требуются; `comparable`, только если нужны `==`, `!=` или map key.
- Используйте `~int`, `~string` и другие approximation terms, когда алгоритм должен работать с defined types на том же underlying type и сохранять их в результате.
- Не называйте constraint по свойству значения (`PositiveInteger`, `ValidID`), если он описывает только множество типов. Валидируйте значения отдельной логикой.
- Для сложного равенства, сортировки или сравнения принимайте явную функцию (`equal`, `less`), а не пытайтесь расширить constraint до нечитаемого type set.
- Возвращайте нулевое значение unknown `T` через `var zero T`; не возвращайте `nil`, если `T` может быть числом или структурой.
- Не рассчитывайте, что слайс `[]T` можно присвоить `[]any`. Если нужен обобщённый код, принимайте `[]T`.

## Generic-типы

- Документируйте нулевое значение generic-типа так же, как у обычного: например, можно ли вызвать `Add` у нулевого `Set`.
- Помните, что map не гарантирует порядок. API `Set.Values()` не должен неявно обещать сортировку.
- Не добавляйте `Optional[T]`, Result-типы и универсальные коллекции только потому, что они есть в другом языке. Сначала сравните их с привычными `(T, bool)`, `error`, `[]T` и `map`.
- Параметризованный repository или service вводите только при доказанной общей модели операций. Не скрывайте за CRUD-абстракцией авторизацию, транзакции, инварианты и разный жизненный цикл сущностей.

## Проверка и эволюция

- Тестируйте generic-алгоритм на встроенном и defined type с тем же underlying type.
- Держите type set компактным: расширение `int | int64` до большого списка — изменение публичного контракта.
- Оценивайте generics сначала по понятности API и отсутствию дублирования, а производительность — только по benchmark и profile.
- Перед добавлением type parameter убедитесь, что есть несколько реальных применений и одно ясное имя общей операции.

## Итоговый чек-лист

- [ ] Новый type — defined type, если нужна защита смысла, а alias — только для совместимости.
- [ ] Внешние строки, JSON и path-параметры проверяются до преобразования в domain type.
- [ ] Constraint соответствует операциям в теле функции и не шире необходимого.
- [ ] `~` добавлен осознанно, чтобы поддержать семейство defined types.
- [ ] Generic-контейнер документирует нулевое значение, изменяемость и порядок.
- [ ] Domain-операции Task Manager не спрятаны в искусственный `T`/`K`/`V` API.
- [ ] Тесты подтверждают поведение для нескольких конкретных подстановок типов.
