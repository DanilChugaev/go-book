# Обработка ошибок

## Цель урока

Научиться возвращать и обрабатывать ошибки через тип `error`, добавлять к ним контекст и проверять причину ошибки с помощью `errors.Is`.

В Task Manager API метод `Rename` больше не будет возвращать только `true` или `false`. Вместо этого он сообщит вызывающему коду, почему новое название не подходит.

## Ошибки — обычные значения

В Go ошибка обычно возвращается как последнее значение функции. Тип `error` — это интерфейс с методом `Error() string`.

```go
func findTask(id int) (Task, error) {
	// ...
}
```

Если операция успешна, ошибка равна `nil`. Если возникла проблема, функция возвращает значение `error`, а результат операции часто имеет нулевое значение.

```go
task, err := findTask(42)
if err != nil {
	fmt.Println("Не удалось найти задачу:", err)
	return
}

fmt.Println(task.Title)
```

Такой стиль делает возможные ошибки видимыми в сигнатуре функции и заставляет вызывающий код осознанно решить, что с ними делать.

## Создание ошибки: `errors.New`

Пакет `errors` создаёт простую ошибку с текстом:

```go
import "errors"

var ErrEmptyTitle = errors.New("название задачи не должно быть пустым")
```

Ошибки, которые обозначают важные повторяющиеся причины, удобно объявлять как переменные на уровне пакета:

```go
var (
	ErrTaskIsNil   = errors.New("задача не существует")
	ErrEmptyTitle  = errors.New("название задачи не должно быть пустым")
	ErrTitleTooLong = errors.New("название задачи слишком длинное")
)
```

Имена таких переменных начинаются с `Err`. Позднее, когда появятся пакеты, экспортируемые ошибки позволят другому пакету проверить конкретную причину без сравнения текстов.

Не создавайте новую ошибку в каждом месте, если вызывающему коду важно распознать именно её причину:

```go
// Менее удобно для последующей проверки причины:
// return errors.New("название задачи не должно быть пустым")

return ErrEmptyTitle
```

## Обработка: `if err != nil`

Стандартный паттерн — проверить ошибку сразу после вызова и выйти по раннему `return`:

```go
func printTaskTitle(task *Task) {
	if err := task.Rename("Купить продукты"); err != nil {
		fmt.Println("Не удалось переименовать задачу:", err)
		return
	}

	fmt.Println("Новое название:", task.Title)
}
```

Так успешный путь остаётся без лишней вложенности:

```go
// Менее читаемо, если успешный код становится большим:
if err == nil {
	// успешный путь
} else {
	// обработка ошибки
}
```

## Метод `Rename` возвращает error

Перепишем метод Task Manager API. Метод `Complete` по-прежнему меняет признак выполнения и не выполняет валидацию. А `Rename` может не выполниться из-за некорректного входного значения, поэтому он возвращает ошибку.

```go
package main

import (
	"errors"
	"fmt"
)

var (
	ErrTaskIsNil    = errors.New("задача не существует")
	ErrEmptyTitle   = errors.New("название задачи не должно быть пустым")
	ErrTitleTooLong = errors.New("название задачи слишком длинное")
)

type Task struct {
	ID        int
	Title     string
	Priority  int
	Completed bool
}

func (task *Task) Complete() {
	task.Completed = true
}

func (task *Task) Rename(title string) error {
	if task == nil {
		return ErrTaskIsNil
	}

	if len(title) == 0 {
		return ErrEmptyTitle
	}

	if len(title) > 120 {
		return ErrTitleTooLong
	}

	task.Title = title
	return nil
}

func main() {
	task := Task{ID: 1, Title: "Купить молоко", Priority: 2}

	if err := task.Rename("Купить продукты"); err != nil {
		fmt.Println("Ошибка:", err)
		return
	}

	task.Complete()
	fmt.Println(task.Title, task.Completed)
}
```

Возврат `nil` означает, что операция выполнена успешно.

::: warning Не игнорируйте error
Если функция возвращает ошибку, не присваивайте её в `_` только ради того, чтобы скомпилировать код. Сначала решите, что должно произойти при неудаче: вернуть ошибку выше, показать сообщение, повторить операцию или выбрать другое значение.
:::

## Контекст ошибки: `fmt.Errorf`

Иногда одного сообщения причины недостаточно. Добавьте контекст через `fmt.Errorf`:

```go
func renameTask(task *Task, title string) error {
	if task == nil {
		return fmt.Errorf("не удалось обновить задачу: %w", ErrTaskIsNil)
	}

	if err := task.Rename(title); err != nil {
		return fmt.Errorf("не удалось обновить задачу %d: %w", task.ID, err)
	}

	return nil
}
```

`%w` оборачивает исходную ошибку. Получившийся текст будет содержать и контекст, и причину:

```text
не удалось обновить задачу 1: название задачи не должно быть пустым
```

Используйте `%w`, когда вышестоящему коду может понадобиться узнать исходную причину. Обычный `%v` только вставляет текст ошибки и не сохраняет связь для `errors.Is`.

Проверка `task == nil` находится перед обращением к `task.ID`: это позволяет безопасно обернуть и такую ошибку.

## Проверка причины: `errors.Is`

Не сравнивайте текст ошибки: он предназначен для человека и может измениться. Если ошибка обёрнута, не всегда сработает и `err == ErrEmptyTitle`.

Используйте `errors.Is`:

```go
err := renameTask(&Task{ID: 1}, "")

if errors.Is(err, ErrEmptyTitle) {
	fmt.Println("Попросите пользователя указать название")
}
```

`errors.Is` ищет указанную ошибку внутри цепочки, которую создал `%w`.

Полный пример:

```go
func renameTask(task *Task, title string) error {
	if task == nil {
		return fmt.Errorf("не удалось обновить задачу: %w", ErrTaskIsNil)
	}

	if err := task.Rename(title); err != nil {
		return fmt.Errorf("не удалось обновить задачу %d: %w", task.ID, err)
	}

	return nil
}

func main() {
	task := &Task{ID: 1, Title: "Купить молоко", Priority: 2}

	err := renameTask(task, "")
	if err == nil {
		return
	}

	if errors.Is(err, ErrEmptyTitle) {
		fmt.Println("Введите название задачи")
		return
	}

	fmt.Println("Неожиданная ошибка:", err)
}
```

## Когда возвращать error

Возвращайте `error`, когда вызывающий код должен узнать, что операция не выполнилась, и может на это повлиять. Например:

- входные данные не прошли валидацию;
- задача не найдена по ID;
- не удалось прочитать файл;
- внешний сервис или база данных вернули проблему.

Не используйте `error` для обычной ветви успешной логики. Например, метод `Summary() string` не должен возвращать ошибку, если он всегда умеет собрать строку из полей структуры.

## Частые ошибки

### Сообщение вместо проверки ошибки

```go
if err.Error() == "название задачи не должно быть пустым" {
	// Хрупко: текст может измениться.
}
```

Для известных причин используйте `errors.Is(err, ErrEmptyTitle)`.

### `%v` вместо `%w` при оборачивании

```go
// return fmt.Errorf("не удалось переименовать: %v", err)
return fmt.Errorf("не удалось переименовать: %w", err)
```

`%w` сохраняет исходную ошибку для `errors.Is`.

### Продолжение после ошибки

```go
if err := task.Rename(""); err != nil {
	fmt.Println(err)
}

fmt.Println(task.Title) // Код продолжится, хотя операция не выполнилась.
```

Если дальнейший код зависит от успеха операции, после обработки ошибки сделайте `return`, `continue` или другой явный переход.

### Panic вместо ошибки в обычной валидации

Пустое название — ожидаемая ошибка пользовательского ввода, а не авария программы. Возвращайте `error`; `panic` оставьте для действительно невозможных состояний или внутренних ошибок библиотек. `panic`, `defer` и `recover` разберём отдельно, когда появится практический контекст.
