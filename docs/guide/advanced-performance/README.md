# Продвинутый Go D: производительность и диагностика

## Цель главы

Научиться измерять производительность Go-кода воспроизводимо: формулировать гипотезу, писать benchmark, сравнивать изменения через `benchstat`, снимать CPU и memory profiles, интерпретировать `pprof`, понимать аллокации и применять `strings.Builder` или `sync.Pool` только после подтверждённого измерениями выигрыша.

Эта глава не о том, как сделать любой код «максимально быстрым». Она о безопасном инженерном цикле:

```text
симптом → метрика → воспроизводимый сценарий → профиль/benchmark
   ↓                                                ↓
проверка после изменения ← минимальное понятное исправление
```

Для Task Manager API симптомом может быть медленный `GET /tasks`, высокий расход памяти при JSON-экспорте или рост CPU после появления фильтрации. До измерения нельзя уверенно утверждать, что проблема в строках, SQL, кодировании JSON, HTTP-клиенте, блокировках или инфраструктуре.

## Сначала измерение, потом оптимизация

Оптимизация без измерений обычно имеет один из трёх результатов:

- код становится сложнее, но не быстрее в реальном сценарии;
- улучшена редкая функция, а bottleneck остался в SQL, сети или JSON;
- microbenchmark показывает выигрыш, но production ухудшается из-за блокировок, памяти или более сложного протокола.

Вместо вопроса «как ускорить этот фрагмент?» начните с вопросов:

1. **Что именно плохо для пользователя или системы?** p95 latency, CPU, RSS, число аллокаций, стоимость инфраструктуры?
2. **Где это проявляется?** Один endpoint, CLI-экспорт, worker, тест, нагрузочный сценарий?
3. **Как воспроизвести сценарий?** Набор данных, настройки, запрос, версия Go, машина и команда.
4. **Какова гипотеза?** «Экспорт создаёт много промежуточных строк», а не «нужно добавить pool».
5. **Как будет подтверждён результат?** Те же benchmark/profile, функциональные тесты и, если нужно, нагрузочный тест.

::: tip Производительность — свойство сценария
`strings.Builder` может улучшить формирование большого текста, но ничего не изменит, если 95% времени занимает PostgreSQL. Увеличение числа worker может ускорить I/O до лимита внешнего API, а после него повысить ошибки и p99. Измеряйте реальный путь, а не только отдельную понравившуюся строку кода.
:::

## Что измеряет Go

`go test` и `pprof` показывают разные стороны проблемы:

| Инструмент | Вопрос | Основные показатели |
| --- | --- | --- |
| benchmark | Насколько быстро и с какими аллокациями работает конкретная операция? | `ns/op`, `B/op`, `allocs/op` |
| CPU profile | Где процесс тратит процессорное время? | flat/cumulative CPU time |
| heap profile | Какие места создают или удерживают память? | bytes/objects, allocated/in-use |
| block/mutex profile | Где goroutine ждут синхронизацию? | время блокировок/конфликтов |
| load test / метрики | Как система ведёт себя под реалистичной нагрузкой? | throughput, latency percentiles, errors, saturation |

Ни один из них не заменяет остальные. Benchmark не показывает поведение базы и сети; CPU profile не доказывает, что endpoint удовлетворяет p99; heap profile не заменяет проверку отсутствия утечки.

## Стабильное окружение

Микроизмерения шумны: на них влияют scheduler, фоновая нагрузка, thermal throttling, версия компилятора, частота CPU и соседние процессы. Сделайте сравнение честнее:

- измеряйте на одной машине и одной версии Go;
- не сравнивайте результаты ноутбука на батарее с CI на shared runner;
- закройте тяжёлые приложения и не запускайте параллельно большую сборку;
- фиксируйте входные данные и размер сценария;
- запускайте benchmark несколько раз (`-count`) и сравнивайте статистически;
- фиксируйте команду, commit и изменение конфигурации рядом с результатом.

Абсолютное число `ns/op` редко переносимо между машинами. Важнее сравнение до/после в сопоставимых условиях и понимание, что именно оно измеряет.

## Сначала проверьте корректность

Оптимизация не оправдывает изменение контракта. Перед benchmark и после изменения запускайте обычные проверки:

```bash
go test ./...
go test -race ./...
go vet ./...
```

Для HTTP-изменений сохраните handler-тесты: быстрый JSON-ответ с другой семантикой фильтра, пропущенной ошибкой или гонкой данных не является улучшением.

## Пример гипотезы: экспорт задач

Допустим, JSON-экспорт 100 000 задач стал медленным. Не начинайте с переписывания всего на ручную сериализацию. Сначала зафиксируйте:

```text
Сценарий: сериализация 100 000 Task в JSON без файлового I/O.
Метрика: ns/op, B/op, allocs/op и CPU profile.
Гипотеза: значительную долю CPU или памяти создаёт конкретная подготовка данных,
а не json.MarshalIndent сам по себе.
Критерий: после изменения результат идентичен, benchmark стабильно улучшен,
а profile показывает уменьшение именно предполагаемого узкого места.
```

Отделите сериализацию от записи файла и сети. Если измерять всё вместе, результат может отражать filesystem cache, диск или docker volume вместо кода, который вы хотите изучить.

## Измеряемая единица работы

Хороший benchmark имеет одну понятную операцию:

- построить текст экспорта из заранее созданных задач;
- отфильтровать слайс из N задач;
- кодировать один DTO в JSON;
- распарсить один запрос;
- выполнить один in-memory метод.

Плохой benchmark смешивает инициализацию, случайные данные, вывод в stdout, sleep, HTTP-сервер и проверку результата внутри основного цикла. Он измеряет случайный набор действий и хуже объясняет причину числа.

Следующая страница покажет, как оформить измеряемую единицу как benchmark и не обмануть себя setup-кодом или оптимизациями компилятора.
