# Рекомендации по коду: производительность и диагностика

## Методика

- Начинайте с наблюдаемого симптома и важной метрики: latency, throughput, CPU, allocation rate, retained heap или contention.
- Фиксируйте сценарий: размер и форму входа, конфигурацию, версию Go, команду, commit и окружение измерения.
- Формулируйте проверяемую гипотезу до изменения; не выбирайте `Builder`, `Pool` или concurrency как заранее известное лекарство.
- Сохраняйте функциональный контракт: до и после запускайте unit-тесты, `go vet` и `go test -race`, если изменения затрагивают конкурентный код.
- Предпочитайте сокращение ненужной работы — пагинацию, batching, правильный SQL и устранение N+1 — микрооптимизации локального кода.

## Benchmarks

- Делайте одну понятную операцию на benchmark-итерацию; preparation, random input и I/O выносите из измеряемого цикла, если они не являются объектом измерения.
- Используйте `b.Loop()` в поддерживаемой версии Go либо корректный цикл по `b.N`; сохраняйте результат в sink, чтобы вычисление не исчезло.
- Включайте `b.ReportAllocs()` или запускайте с `-benchmem`, если исследуете память.
- Используйте sub-benchmarks для разных размеров входа и имена, которые объясняют сценарий.
- Не делайте вывод по одному запуску. Сравнивайте серии одинаковых запусков через `benchstat`.
- Не переносите абсолютные `ns/op` между разными машинами, версиями Go и режимами питания как универсальный факт.

## Profiles и память

- CPU profile отвечает на вопрос о процессорном времени; heap profile различает всего выделенную (`alloc_space`) и удерживаемую (`inuse_space`) память.
- Начинайте исследование `pprof` с `top`, `top -cum` и `list`; смотрите callers, а не только строку с большим flat time.
- Снимайте profile при стабильной репрезентативной нагрузке. Idle profile почти ничего не говорит о стоимости endpoint.
- Сравнивайте до/после через `pprof -base` только при одинаковом сценарии и подтверждайте вывод benchmark-серией.
- Не считайте высокий allocation rate автоматической утечкой; ищите удерживаемые ссылки и рост `inuse_space` после GC.
- Держите runtime pprof вне публичного router, ограничивайте loopback/internal network и не публикуйте profiles без проверки содержимого.

## Аллокации и точечные оптимизации

- Используйте `go test -gcflags='-m=2'` как диагностику решения компилятора, а не как требование устранить каждый escape.
- Применяйте `strings.Builder` для большого текста в цикле; для короткой простой конкатенации оставляйте читаемый код, пока benchmark не доказал проблему.
- `Grow` — ограниченная эвристика. Не рассчитывайте размер из недоверенного или неограниченного внешнего ввода.
- Не меняйте immutable `string` API на mutable `[]byte` без явных правил ownership и подтверждённой необходимости.
- Используйте `sync.Pool` только для временных объектов в доказанно горячем пути; `Get` может вернуть nil, а runtime может очистить pool.
- Перед `Put` очищайте объект, не возвращайте caller память после `Put` и не сохраняйте чрезмерно большие buffers в pool.
- Никогда не используйте `sync.Pool` как pool соединений, обязательный cache, очередь, канал передачи владения или механизм управления жизненным циклом.

## Итоговый чек-лист

- [ ] Есть симптом, репрезентативный сценарий, baseline и измеряемый критерий успеха.
- [ ] Benchmark измеряет одну операцию, не включает случайный setup и сохраняет результат.
- [ ] Вывод основан на серии запусков и при необходимости подтверждён `benchstat`.
- [ ] Profile объясняет предполагаемый bottleneck, а не служит декоративным артефактом.
- [ ] `alloc_space` не спутан с retained heap или memory leak.
- [ ] Изменение не ухудшило контракт, тестируемость, безопасность данных и понятность кода.
- [ ] `Builder`, `Grow`, `sync.Pool` и другие оптимизации оставлены только при доказанной пользе.
