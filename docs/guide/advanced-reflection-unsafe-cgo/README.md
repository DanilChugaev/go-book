# Продвинутый Go E: reflection, `unsafe` и cgo

## Цель главы

Понять назначение reflection, `unsafe` и cgo, безопасно читать их код в зависимостях, распознавать риски и выбирать обычные типы, интерфейсы, code generation или библиотечную интеграцию, когда эти инструменты не нужны.

Это не глава о том, как «обойти» систему типов Go. У всех трёх механизмов есть законные узкие области применения:

- **reflection** позволяет библиотеке исследовать типы и значения во время выполнения;
- **`unsafe`** открывает низкоуровневые операции с памятью, которые язык обычно запрещает;
- **cgo** вызывает C-код и C-библиотеки из Go.

Но в прикладном Task Manager API они почти никогда не нужны в handler, service, repository или доменной модели. Обычный статически типизированный Go-код лучше проверяется компилятором, проще рефакторится и безопаснее переносится между платформами.

## Карта главы

1. **Эта страница** — границы применения, решения до выбора low-level инструмента.
2. [Reflection: `reflect.Type` и `reflect.Value`](reflection.md) — устройство API, теги, изменяемость и роль в JSON/ORM/framework.
3. [`unsafe`: память и границы гарантий](unsafe.md) — `Sizeof`, `Pointer`, `uintptr`, GC и проверка `checkptr`.
4. [cgo: вызов C-кода из Go](cgo.md) — минимальный вызов, владение памятью, потоки, сборка и критерии отказа.

## Модель принятия решения

Перед использованием reflection, `unsafe` или cgo пройдите по порядку:

1. **Можно ли написать конкретный код?** Для `Task` явный `task.Title` лучше динамического поиска поля по строке.
2. **Подойдёт ли маленький интерфейс?** Если нужен метод `Validate() error`, интерфейс выражает контракт на этапе компиляции.
3. **Можно ли применить generics?** Для алгоритма над `[]T` generic-функция сохраняет информацию о типе без runtime inspection.
4. **Нужна ли code generation?** Для стабильного schema/API protobuf, OpenAPI, SQLC или `go generate` дают проверяемый код заранее.
5. **Есть ли внешняя граница, где динамика неизбежна?** JSON schema, ORM metadata, plugin protocol или существующая C-библиотека могут обосновать специальный инструмент.
6. **Документированы ли контракт, тесты, производительность и ownership?** Если нет — инструмент выбран слишком рано.

```text
конкретный тип → интерфейс/generics → генерация кода → reflection → unsafe/cgo
       проще и безопаснее                              ↑ только при доказанной необходимости
```

Это не абсолютная иерархия. `encoding/json` разумно использует reflection, потому что библиотека должна работать с произвольными пользовательскими структурами. Но приложение, которое знает свой `CreateTaskRequest`, не получает ту же выгоду от универсального runtime validator.

## Цена динамики

| Инструмент | Что даёт | Основная цена |
| --- | --- | --- |
| Reflection | динамический доступ к типам, полям, тегам и методам | runtime panic, меньше проверок компилятором, медленнее и хрупче refactor |
| `unsafe` | работа с представлением памяти | возможные memory corruption, нарушение GC-инвариантов, platform dependence |
| cgo | доступ к C ABI и C-библиотекам | сложная сборка, ownership на двух рантаймах, blocking calls, portability и security surface |

Если одна из этих цен не компенсирована конкретным требованием, предпочтительнее обычный Go.

## Практические роли в экосистеме

### JSON

`encoding/json` использует reflection, чтобы прочитать экспортируемые поля struct и их теги `json:"title"`. Благодаря этому библиотека не требует отдельной функции сериализации для каждой структуры.

Но reflection не заменяет контракт API:

- JSON decoder проверяет форму данных, но не бизнес-правила;
- неизвестные поля и `omitempty` — часть внешнего контракта, которую нужно тестировать;
- handler должен декодировать конкретный DTO, а не принимать `map[string]any` без необходимости;
- custom `MarshalJSON`/`UnmarshalJSON` нужны только для особого формата, не как способ «ускорить всё».

### ORM и frameworks

ORM может по тегам построить SQL schema, web-framework — связать path/query/body со структурой, DI-container — собрать зависимости по типу. Это удобно на интеграционной границе, но скрывает часть поведения от компилятора. При подключении такой библиотеки проверяйте SQL, миграции, ошибки валидации, производительность и поведение при rename полей интеграционными тестами.

### `unsafe` и производительные библиотеки

Некоторые низкоуровневые библиотеки применяют `unsafe` для оптимизации, syscall или zero-copy преобразований. Пользователь библиотеки не должен копировать этот подход в application code. Сперва обновите библиотеку, прочитайте её contract и измерьте реальную проблему.

### C-библиотеки

cgo оправдан, когда есть существующая библиотека с важной функцией: системный SDK, crypto/HSM integration, hardware driver или зрелый native engine. Создайте тонкую изолированную обёртку на границе пакета; не распространяйте `C.*` типы по service и handler.

## Общие правила безопасности

- Держите код с reflection, `unsafe` и cgo маленьким, локальным и хорошо протестированным.
- Не передавайте недоверенный ввод в динамический доступ к полям/методам или в C API без строгой валидации.
- Не превращайте runtime panic в тихое игнорирование ошибки. Проверяйте `Kind`, `IsValid`, `CanSet`, ошибки C API и возвращайте обычный `error` на границе.
- Не делайте предположений о layout struct, размере указателя и порядке полей без явной документированной платформенной причины.
- Запускайте `go vet ./...`, unit/integration tests, `go test -race ./...` при релевантности и несколько target platform сборок для cgo-кода.
- Документируйте minimum Go version, platform/architecture limits, ownership памяти и план замены зависимости.
