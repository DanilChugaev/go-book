# `unsafe`: память и границы гарантий

Пакет `unsafe` существует для runtime, syscall, cgo и небольшого числа системных библиотек. Он позволяет выразить операции, которые обычная система типов запрещает. Название буквально означает: компилятор больше не может гарантировать безопасность памяти.

Для Task Manager API `unsafe` не нужен. Не используйте его для «ускорения» JSON, преобразования строк, доступа к private полям или ручной упаковки сетевых данных без измерения, глубокого понимания lifetime и строгой необходимости.

## Что остаётся безопасным: compile-time layout information

Некоторые операции полезны для диагностики низкоуровневых интеграций:

```go
type header struct {
	Version uint16
	Flags   uint8
	Length  uint32
}

fmt.Println(unsafe.Sizeof(header{}))        // размер в байтах на текущей архитектуре
fmt.Println(unsafe.Alignof(header{}))       // требуемое выравнивание
fmt.Println(unsafe.Offsetof(header{}.Length)) // смещение поля
```

Эти значения зависят от архитектуры, выравнивания и layout компилятора. Они не делают Go struct бинарным network protocol: padding, endianness, версия протокола и проверка длины остаются отдельными задачами. Для внешнего формата обычно используйте явный `encoding/binary`.

```go
func encodeHeader(version uint16, flags uint8, length uint32) []byte {
	data := make([]byte, 7)
	binary.BigEndian.PutUint16(data[0:2], version)
	data[2] = flags
	binary.BigEndian.PutUint32(data[3:7], length)
	return data
}
```

Этот вариант явно фиксирует формат независимо от padding и архитектуры.

## `unsafe.Pointer` и `uintptr`

`unsafe.Pointer` — специальный тип указателя, который можно конвертировать в/из указателей других типов при соблюдении жёстких правил. `uintptr` — целое число, достаточно большое для представления адреса, но **не указатель для garbage collector**.

Главная опасность: если сохранить адрес только как `uintptr`, GC может считать объект недостижимым, переместить/освободить его в будущих реализациях или не сохранить требуемое время жизни. Между отдельными выражениями могут происходить safe points и вызовы runtime.

```go
// Небезопасный анти-паттерн: не храните адрес как uintptr для будущего использования.
address := uintptr(unsafe.Pointer(&task))
// ... произвольная работа, allocations, вызовы функций ...
taskPointer := (*Task)(unsafe.Pointer(address))
```

Не лечите это `runtime.KeepAlive` без точного понимания официальных правил: `KeepAlive` решает отдельные проблемы lifetime для корректно спроектированного low-level кода, а не делает произвольную арифметику адресов безопасной.

## Указательная арифметика не для application code

`unsafe.Add` может сдвинуть pointer на число байтов. Для обычного слайса это почти всегда хуже индексирования:

```go
// Ясно, проверяется bounds check и остаётся переносимым.
priority := priorities[index]
```

Вариант с указателями требует доказать границы, выравнивание и lifetime вручную. Ошибка может не вызвать panic там, где вы ожидаете, а тихо испортить память. Даже если microbenchmark показывает выигрыш, сначала оцените алгоритм, allocation, batch size и I/O: они почти всегда важнее.

## Zero-copy преобразования — риск ownership

Строка в Go неизменяема, а `[]byte` изменяем. Опасные zero-copy преобразования могут позволить одному коду изменить байты, которые другой считает строкой, или сохранить ссылку на буфер после его reuse. Это приводит к data race, повреждённым данным и security bugs.

В обычном коде используйте обычные преобразования:

```go
text := string(data) // создаёт независимую строку
data = []byte(text)  // создаёт независимый слайс
```

Если profile доказал, что копирование — bottleneck, сначала ищите API, который принимает нужный вид данных (`io.Reader`, `io.Writer`, streaming encoder), или меняйте границу ownership. Только изолированная низкоуровневая библиотека с чёткими lifetime guarantees может обсуждать unsafe zero-copy.

## Нельзя обращаться к private полям через unsafe

Reflection не даёт устанавливать неэкспортируемые поля из другого пакета. Это защита инкапсуляции. Обход через `unsafe` нарушает контракт пакета и может сломаться при обновлении зависимости:

```go
// Не делайте так: offset private поля — не public API пакета.
// pointer := unsafe.Add(unsafe.Pointer(value), offset)
```

Если библиотека не предоставляет нужную возможность, используйте её публичный API, расширение, fork с осознанным сопровождением или другую библиотеку. Не делайте внутренний layout скрытой зависимостью production-сервиса.

## Проверки low-level кода

`go vet` содержит проверки подозрительного использования `unsafe.Pointer`, но не доказывает отсутствие всех ошибок. Для дополнительной диагностики указателей запускайте тесты с checkptr:

```bash
go test -gcflags=all=-d=checkptr=2 ./internal/lowlevel
go test -race ./internal/lowlevel
```

`checkptr` ловит часть неправильных преобразований и арифметики, но не заменяет review, тесты на целевых архитектурах и понимание ownership. Нельзя писать код, который работает «только без checkptr», и считать это оптимизацией.

## Когда `unsafe` может быть оправдан

Все условия должны выполняться одновременно:

- есть конкретная измеренная или платформенная необходимость;
- стандартная библиотека, явный binary encoding, конкретный API и code generation не решают проблему;
- код локализован в маленьком internal package;
- в комментарии описаны layout, lifetime, target architectures и причина невозможности обычного решения;
- есть тесты, benchmarks, `vet`, checkptr и проверка на нужных OS/arch;
- есть владелец, который будет сопровождать код при обновлении Go и зависимости.

Для большинства backend-проектов хотя бы одно условие не выполняется. Это достаточная причина отказаться.

## Итог

`unsafe` — не более быстрый Go. Это выход за гарантии языка, который переносит доказательство корректности с компилятора на автора кода. Следующая страница рассмотрит похожую границу — переход между Go и C через cgo.
